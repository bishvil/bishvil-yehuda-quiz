# Historical async results — 2026-11-10

The user reported a missing Sunday game and supplied a results screenshot showing
only one ended game (`633690`, dated 2026-05-11). No production database query or
admin session was available to identify the missing game's exact row.

## Reproduced cause

The old `submit_answer` function allowed async submissions while the global
session remained `scheduled`. The results list included ended sessions and only
`live`/`paused` async sessions. An old async game could therefore have persisted
answers and scores but remain invisible. There was no creation-date cutoff.
The endpoint also stopped silently at 50 results, with no way to reach older
pages. These are independently reproduced application defects; the user's
specific production record has not been inspected.

## Change

- Include `scheduled`, `live` and `paused` async games, preserving their stored
  statuses and scores. Draft async and unfinished sync visibility is unchanged.
- Fetch 50 results per page with a continuation offset, stable timestamp/ID
  ordering and a 51st-row continuation check. Reject malformed offsets.
- Add accessible loading/retry controls for older pages. Preserve already loaded
  results on failure, suppress duplicate requests and deduplicate cards by ID.
- Date cards by end time, then start time, then creation time. Historic sessions
  with no global start/end timestamp still have a visible date. Label async
  interim results explicitly.

This changes reads/display only. No SQL migration, score rewrite, historical
answer modification or forced session completion is required by this patch.
The previous four capability migrations still need to exist in production;
their remote application has not been independently verified.

## Validation

- The new API regression suite initially failed for hidden scheduled history,
  missing continuation and invalid offsets; all 10 cases passed after the fix.
- Full unit/API/integration suite: **473 tests passed in 84 files**.
- Nine results-list UI cases cover paging, retry, duplicate clicks, historical
  dates and accurate interim labels.
- TypeScript, scoped ESLint, formatting and production build passed.
- Browser verification uses an actual local production build and real local
  database rows: 55 newer games, a scheduled async game dated 2026-05-10 with a
  stored answer and 800 points, pagination to that game and its full report.
  Mobile/desktop card screenshots are generated by the regression spec.

See `tests/e2e/admin-results-history.spec.ts` and
`tests/unit/api/admin-results-history.test.ts`. Before calling the user's
specific production game recovered, verify its presence in the deployed report
or inspect its session/answers/score rows in the client's Supabase project.
