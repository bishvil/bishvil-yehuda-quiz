# Load test report — 2026-05-08

Target: 200–400 concurrent participants in one sync-mode game on production
(`https://bishvil-yehuda-quiz.vercel.app`, Supabase project
`dcinzawjietdpbmvksqx` on **Nano** compute, Frankfurt).

## TL;DR

The system as-shipped today does not meet the 200–400 user target.
Two independent bottlenecks were uncovered:

1. **`/api/session/[pin]/join` ~59 % failure rate at 200 VUs** — anonymous
   sign-in via Supabase Auth is rate-limited; we exceed the limit when 200
   participants ramp up in 60 s.
2. **`/api/participant/[pin]/state` saturates DB capacity at 200 VUs** —
   p95 4.8 s, p99 13.5 s, max 47.6 s, with a healthy 571 ms median. The
   long tail is queueing on Nano's single shared vCPU and Supavisor
   transaction pool.

The route refactor we did this session (Promise.all-ing the seven
sequential queries into two parallel waves) is real and helps —
median /state under load is 571 ms, which is fine — but it can't
compensate for the lack of CPU and the Auth rate limit.

## Test context

- Tooling: `k6 v2.0.0-rc1` from `instance-neo`. Repo includes
  `tests/load/{setup,advance,teardown}.mjs` + `k6-sync-game.js`.
- Scenario: `ramping-vus` 0 → N over 60 s, hold N for 180–240 s,
  ramp down. Each VU joins, polls `/state` every 5 s, posts an answer
  when the question id changes. No host-driven advance in this run
  (focused on join + steady poll, the dominant load).
- Production DB started empty; teardown deletes anonymous test users
  + the test quiz cascade.

## Diagnoses

### Bottleneck #1 — Supabase Auth rate limit on `signInAnonymously`

`/api/session/[pin]/join` calls `supabase.auth.signInAnonymously()` for
every participant (`app/api/session/[pin]/join/route.ts:81`). Supabase
applies hard rate limits on this endpoint by IP + project. With 200 VUs
ramping in 60 s we burn through the per-minute budget instantly and 366
of 620 join attempts fail. Joins that did go through completed in
under 1 s, so it's not a latency issue — it's a rejection.

This is **not solvable by upgrading compute**. Options:

1. **Raise the anonymous-sign-in rate limit** in the Supabase dashboard
   (Auth → Rate Limits → "Anonymous sign-ins"). Per-minute and per-hour
   knobs are available; default is conservative.
2. **Stop using `signInAnonymously` for joins**. The current model
   creates a real `auth.users` row per participant. An alternative
   (cheaper at scale) is to mint a short-lived signed JWT per participant
   on the server side using the JWT secret, with custom claims for
   session_id / participant_id. That bypasses the Auth rate limit and
   removes per-join writes to `auth.users`. This is a bigger refactor.

### Bottleneck #2 — Nano DB capacity for `/state` at 200 RPS

The healthy 571 ms median says the refactored route is fine on a warm
path. The p95 4.84 s / max 47.6 s tail is classic queue-on-saturation:
some fraction of requests waits behind others for a free vCPU slice or
pooler slot.

Nano is 1 shared vCPU / 512 MB RAM / 200 pooler conns. At 200 VUs
sustaining 28.8 RPS through this route plus the join writes, we're
pegged. Upgrade options (downgradable any time):

- **Small** ($15 / mo) — 2 vCPU shared, 2 GB RAM, 400 pooler conns.
  Likely enough for 200 users. Borderline for 400.
- **Medium** ($60 / mo) — 4 GB RAM, 600 pooler conns. Comfortable for
  400.

Code-side, two more low-risk wins remain (not done in this session):

- Cache `quiz.title/brand_id/custom_logo` and `totalQuestions` per
  `quiz_id` for the duration of a session. They never change while a
  game is live. Saves two of the five Wave-A queries per poll. Implement
  via Vercel Runtime Cache or React `cache()` per session.
- Batch the Wave-A queries into one Postgres RPC. Single round-trip
  through Supavisor instead of five concurrent ones. Bigger work, but
  cuts pooler pressure significantly.

## Recommendations, ordered by ROI

1. **Raise anonymous sign-in rate limits** in Supabase Auth settings.
   No code change. Required before any further load testing.
2. **Upgrade Supabase compute to Small ($15/mo)**, re-run the 200 VU
   test. Decide on Medium based on actual numbers.
3. **Cache the session-static lookups** (`quiz`, `totalQuestions`)
   inside `/state`. Cuts Wave A from five queries to three.
4. (Stretch) **Replace `signInAnonymously` with a server-minted JWT**
   for the participant join flow. Removes the per-join auth.users
   write and dependence on Auth rate limits entirely.
