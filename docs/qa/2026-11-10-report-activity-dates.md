# Report activity dates — 2026-11-10

After historical games became visible, the user reported a card showing a May
date for a game played more recently. The prior card displayed the first of
`ended_at`, `started_at` and `created_at` without saying which it was. These are
session lifecycle dates; an open session's end field can also be an expiry.
They do not establish the most recent participation in a reused async game.
The customer's exact cloud timestamps were not available for direct inspection.

## Behavior

- Add `lastPlayedAt`: the later of the latest saved answer's `submitted_at` and
  an actually opened question's non-null progress `started_at`.
- Add `lastJoinedAt` separately. The UI labels this as a join when no played
  activity is available, rather than claiming that joining means answering.
- Limit each embedded relation to one row per session, using explicit direct
  foreign-key relationships to avoid ambiguous many-to-many embedding. The
  existing session query retrieves all three dates without per-session requests
  or complete answer histories.
- Display the first valid date with a visible label: last activity, last join,
  actual closed-session end, session start or creation. Open sessions never use
  the end/expiry field as a played date. Invalid/missing dates fall through;
  no current-time or assumed-Sunday timestamp is invented.
- Score-summary `last_updated_at` is not activity: a backfill or recalculation
  can change it without a participant playing. It is deliberately excluded.
- Data is read-only: no dates, scores or answers are rewritten and no migration
  is added. Report pagination remains ordered by session creation and stable ID;
  this change does not imply a global activity-date sort.

## Validation

- **483 tests passed in 84 files**, including 13 API history/date cases and 16
  results-list UI cases. New activity API cases failed before implementation.
- Real Postgres cases cover May creation plus November answers, a later score
  summary repair, null GPS starts, opened information/unanswered stations,
  no-activity sessions, and independently limited per-session join dates.
- TypeScript, scoped ESLint, formatting and production build passed.
- The production-build Chromium regression verifies an old May-created async
  game showing its saved November 8 activity, score and full report after
  pagination. Mobile and desktop card screenshots are generated by the spec.

Production confirmation is the deployment status plus the user's check of their
actual report. A remaining discrepancy in a specific game's answer timestamps
requires inspecting those cloud records; the application must not silently
change historical data to match an expected date.
